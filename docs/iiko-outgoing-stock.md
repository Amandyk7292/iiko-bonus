# Расходные накладные и остатки витрины

После проведения расходной накладной в iiko товары автоматически вычитаются из
остатка соответствующего филиала Bulka. Это относится ко всем расходным накладным,
включая выдачу блогерам по бартеру: название контрагента не влияет на списание.
Черновик и печать документа сами по себе не уменьшают остаток.

## Как работает синхронизация

Серверный worker `iiko-outgoing-stock` раз в минуту читает
`documents/export/outgoingInvoice` через существующий клиент iiko Dashboard.
Он начинает работу через 15 секунд после запуска backend. Временная недоступность
iiko оставляет курсор на месте; после восстановления worker повторяет запрос.
Отсутствие сети iiko не отключает readiness всего клиентского API.

Ключ операции — город и UUID документа. В одной транзакции PostgreSQL сохраняются
изменение остатка и запись в `iiko_outgoing_stock_documents`. Потерянный ответ,
повторная отправка, перезапуск backend и второй экземпляр worker не списывают товар
повторно. Lease в базе исключает одновременно работающие циклы одного города.
Chain и RMS одного города нельзя подключать как два параллельных источника.

Журнал уже обработанных документов читается пакетами по 100 ID с таймаутом.
Неизменённые документы и неучтённая история до начала синхронизации не вызывают
отдельных операций списания. Изменения известных документов, включая перенос
даты назад, обязательно проходят проверки SQL; неполный ответ журнала прерывает цикл.

| Ситуация | Поведение |
|---|---|
| Накладная `PROCESSED`, товар есть в ручном остатке | Количество уменьшается |
| Накладная `NEW` | Списания нет |
| Повтор без изменений | Списания нет |
| Количество в проведённой накладной изменилось | Учитывается разница |
| Ранее учтённый документ явно вернулся в `NEW` или `DELETED` | Возвращается фактически списанное количество, если после выдачи не было пересчёта |
| Документ исчез из ответа API | Возврата нет: отсутствие не доказывает отмену |
| После выдачи выполнен ручной или Front-пересчёт | Старый документ не вычитается повторно и его отмена не увеличивает новый пересчитанный остаток |
| Пришёл новый товар через «Добавили» | Это прибавка; более ранняя выдача по накладной по-прежнему учитывается |
| Остаток меньше выдачи | Остаток ограничивается нулём, в журнале фиксируется нехватка и требуется сверка |
| Единица накладной не совпадает с единицей учитываемого товара | Документ не применяется, worker показывает ошибку; после исправления единиц повторяет его |
| Дату уже учтённой накладной перенесли через границу пересчёта | Требуется новая физическая сверка; worker не угадывает, включалась ли выдача в старый пересчёт |
| Остаток неизвестен | Количество не выдумывается |
| Остаток ведётся абсолютными снимками iiko | Повторного вычитания нет |
| Включён общий учёт Front | Накладная применяется к общему остатку, защищённому от перезаписи снимками |

`amount` относится к `amountUnit` строки; при отсутствии `amountUnit` используется
основная единица товара. Килограммы не переименовываются в штуки. Поддерживаются
дробные количества до 0,001 с проверкой шага товара в базе.

Новые документы проверяются каждый цикл. Дополнительно сохраняется курсор обхода
семидневных диапазонов от начала учёта: это позволяет догнать длительный простой
и обнаружить исправления старых документов. Документы до первого запуска worker
для города автоматически не импортируются, чтобы не списать весь исторический
архив с текущей витрины. Выдачи задним числом до этой границы требуют сверки.

## Настройка Актау и Астаны

Нужны миграция `20260926113000_iiko_outgoing_stock.sql`, backend с новым worker,
`RUN_BACKGROUND_WORKERS=true`, `RUN_IIKO_OUTGOING_SYNC=true` и действующие учётные
данные iiko Dashboard для обоих городов. По умолчанию
`IIKO_OUTGOING_CITIES=aktau,astana`; отсутствие обязательного города в привязках
видно как `IIKO_OUTGOING_MAPPING_INCOMPLETE`, а доступные города продолжают работу.

12 проверенных соответствий Актау используются из
`src/config/bought-together-branches.js`. Дополнения и замены задаются отдельно:

```json
{
  "UUID-филиала-Bulka": {
    "serverId": "astana-chain",
    "departmentId": "UUID-подразделения-iiko"
  }
}
```

Этот объект помещается в `IIKO_OUTGOING_BRANCHES_JSON`. Значение `null` отключает
конкретную стандартную привязку. Названия филиалов и город сами по себе не являются
доказательством соответствия. Склад строки (`storeId` либо `defaultStoreId`) связывается
с подразделением через `corporation/stores.parentId`, затем с филиалом по этой карте.
Для Астаны идентификатор товара сохраняет префикс `astana:`, как остальная интеграция.

На рабочем сервере `node scripts/list-iiko-outgoing-bindings.js` выводит только
ID/названия/адреса филиалов и подразделений обоих Chain для проверки соответствий.
Флаг `--rms` дополнительно читает подразделения отдельных кассовых серверов.
Скрипт не меняет настройки или остатки и не выводит секреты.

При проверке рабочего сервера 26.09.2026 подтверждены доступ к обоим Chain и
экспорт расходных накладных. В Астане адреса пяти активных филиалов приложения
не совпадают с адресами пяти организаций iiko. До подтверждения владельцем
точных соответствий привязки Астаны не создаются; код поддерживает оба города.
В Актау используются 12 проверенных привязок. Дополнительный активный филиал
«26 мкр 19/3» также требует подтверждения: подразделение iiko называется
«26-й мкр 25». Количество филиалов и похожие названия не заменяют проверку ID.

## Проверка после установки

1. На тестовом товаре установить известный остаток, например 10 штук.
2. В iikoFront создать расходную накладную на 2 штуки и отправить на сервер.
3. Проверить статус `PROCESSED` и остаток 8 после синхронизации.
4. Повторно открыть/отправить тот же документ: остаток остаётся 8.
5. Повторить для Астаны и проверить, что остаток другого филиала не изменился.
6. Отключить связь с iiko, провести ещё одну накладную, восстановить связь:
   документ учитывается после появления на сервере, без двойного списания.

Локальные регрессии: `test/iiko-outgoing-stock.test.js` исполняет SQL в PGlite;
`test/iiko-outgoing-sync.test.js` проверяет XML, привязки, единицы, курсор, lease
и потерянные ответы. Реальная касса и рабочая база при этих тестах не изменяются.
