# Остатки iikoFront и Bulka

## Привязка товара

Остаток связан с UUID товара iiko и филиалом. Название, дефис, фотография
и переводы не участвуют в сопоставлении. Редактируйте импортированную позицию
iiko в меню Bulka: её ID сохраняется при переименовании. Для второго профиля
iiko используется пространство имён `astana:<UUID>`.

Например, «Хот дог» в iiko и «Хот-дог» / «Hot dog» в Bulka имеют один ID.
Два разных товара с одинаковым названием не объединяются.
Отдельно созданный «свой товар» Bulka не получает связь с iiko автоматически.
Для синхронизации используйте импортированную позицию; автоматического
сопоставления по похожести названий нет.

## Источник количества

Плагин 1.3.0 передаёт полный снимок количественного стоп-листа главной кассы
через `POST /api/loyalty/inventory/snapshot`. Нужны общий транспортный ключ
и отдельный ключ конкретного филиала. Один филиал привязывается к одной
группе терминалов; остальные кассы группы не становятся вторым отправителем.

Изменение стоп-листа или заказа запрашивает передачу на следующем цикле
плагина (1 секунда). Контрольный снимок отправляется каждые 15 секунд.
Реальное время обновления зависит также от iikoFront и сети. Повторы и
устаревшие снимки отклоняются. После подключения Front облачный опрос
больше не перезаписывает остатки этого филиала.

Это количественный стоп-лист iikoFront, а не складской бухгалтерский остаток
iikoOffice. Для штучных товаров нужно задать количество в iikoFront.
Ноль запрещает продажу. Удаление позиции из количественного стоп-листа
означает отсутствие ограничения. Дробное количество округляется вниз;
для нескольких размеров одной позиции берётся минимальный остаток.
Отдельный учёт размеров и весовых единиц в текущем каталоге не реализован.
Максимум одного полного снимка — 450 позиций; большие снимки не обрезаются.

## Онлайн-заказ, который также пробивается на кассе

Для каждого товара с заданным остатком последняя единица остаётся на кассе.
Доступно онлайн: `max(0, количество на точке − онлайн-резервы − 1)`.
При остатке 1 заказать через приложение или сайт нельзя; при остатке 2 можно
заказать 1, при остатке 6 — максимум 5. В стоп-листе кассира по-прежнему виден
физический остаток. Неизвестный / неограниченный остаток не превращается в ноль.
Ограничение проверяется в каталоге, расчёте заказа и SQL-резерве под блокировкой
строки товара, а также при подтверждении или восстановлении резерва оплаты.
Уже подтверждённые заказы повторная проверка не отменяет. Уведомление о наличии
не отправляется, если осталась только последняя единица.

Физическое количество уменьшает iikoFront. Bulka вычитает из доступного
количества свои активные резервы до выдачи онлайн-заказа. После выдачи резерв
снимается; повторного уменьшения количества Front и повторного создания
заказа в iiko нет. Между пробитием на кассе и выдачей доступное количество
может временно быть меньше на величину ещё действующего резерва.

Резерв Bulka не блокирует офлайн-продажу на кассе. Эта интеграция синхронизирует
остатки, но сама по себе не обеспечивает атомарную продажу последней единицы
одновременно в iikoFront и интернете. Для этого нужна двусторонняя интеграция
резервов с сопоставлением конкретного онлайн-заказа и заказа кассы.
Буфер в одну единицу уменьшает риск, но не блокирует одновременную офлайн-продажу
нескольких единиц, уже зарезервированных онлайн. Само добавление в корзину
не резервирует товар: резерв создаётся перед началом оплаты.

Выбранный кассиром тип оплаты «Безналичный» не создаёт такую связь. Если к
этому чеку ещё раз привязать бонусного клиента, его отдельный ID не позволит
автоматически распознать уже учтённую онлайн-покупку. До внедрения связи
онлайн-заказ пробивается один раз без повторного применения бонусов.
Выдача на планшете сама по себе не подтверждает пробитие чека в iikoFront.

## Резервное управление кассиром

Если главная касса не присылает снимок 45 секунд, новые онлайн-резервы
по её неподтверждённым остаткам блокируются. Уже оплаченные заказы сохраняются.
Кассир может указать пересчитанное количество вручную в «Стоп-листе».
Ручной остаток используется до отдельного подтверждения «Вернуть iikoFront».
Восстановление связи само его не заменяет. Ручной остаток уменьшается при
выдаче заказа Bulka; отмена его не расходует.

Изменение количества и стоп-листа требует подтверждения. Параллельная
правка с устаревшей ревизией возвращает конфликт вместо потери новых данных.
Кассир видит и редактирует только назначенный ему филиал.
Само переключение стоп-листа не переводит количество Front в ручной режим.

## Установка и проверка на кассе

1. Сохранить действующую папку плагина и её конфигурацию. Закрыть iikoFront
   в согласованное время, заменить DLL и Manifest из пакета 1.3.0.
   Не заменять рабочие секреты шаблоном из пакета.
2. Сохранить в конфигурации ключи лояльности, `IIKO_BRANCH_ID` и
   `IIKO_BRANCH_POS_TOKEN` этой точки. Включить `IIKO_STOCK_SYNC_ENABLED=true`.
3. Запустить главную кассу. В «Статус Bulka» проверить время синхронизации,
   а в экране кассира — «iikoFront подключён».
4. На тестовой позиции задать 10, пробить обычную продажу 5, убедиться,
   что приложение показывает 5. Проверить стоп-лист, отмену продажи,
   переименование, резерв онлайн-заказа и его выдачу.
5. Проверить потерю связи, ручной остаток и явный возврат к iikoFront.

Сборка использует существующий SDK проекта V9Preview7 (9.4.7024-alpha).
На другую версию кассы пакет необходимо проверить отдельно.
Автотесты проверяют серверный расчёт и интерфейс; проверка на физической
кассе обязательна перед утверждением, что конкретный филиал подключён.

Официальное описание API: [количественный стоп-лист iikoFront](https://iiko.github.io/front.api.doc/2023/05/03/stop-list-edit.html).
