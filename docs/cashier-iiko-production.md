# Акт приготовления из кассового отчёта

Кассир выбирает блюда из «Добавлено в витрину» за дату своей единственной назначенной точки. Сервер создаёт один акт iiko из выбранных положительных приходов. Он не вызывает `record_pos_production` и не изменяет остатки Bulka повторно: приход уже записан в неизменяемом журнале.

## Настройка точки

Владелец или администратор явно выбирает сервер своего города, подразделение и склады списания сырья/прихода продукции. Оба склада должны принадлежать выбранному подразделению в актуальном справочнике iiko. Нет автоматического сопоставления по названию точки или первого склада из списка. Без настройки отправка отключена.

`cashier_iiko_production_bindings` хранит это сопоставление отдельно от остатков. `postImmediately=false` отправляет статус `NEW`; `true` отправляет `PROCESSED`. По умолчанию используется черновик. Режим вместе со складами фиксируется в запросе и не меняется при последующей правке настройки.

## Источник количества и API

`GET /admin/api/staff/reports/production?date=YYYY-MM-DD` возвращает точку, доступность, неиспользованные группы блюдо+единица и историю запросов за дату. Количество — сумма `after_quantity-before_quantity` только для `reason=receipt`, ненулевого исходного количества и положительного изменения. Корректировки, пересчёты, начальные остатки и продажи не входят в акт. Период соответствует текущему кассовому отчёту: местная полночь `Asia/Aqtau` включительно до следующей полуночи исключительно, с учётом сброса отчёта. Пагинация журнала не ограничивает суммы.

Сервер проверяет исходный ID блюда на выбранном сервере и основную единицу iiko. ID Астаны преобразуются из внутреннего префикса `astana:`, произвольные пользовательские ID не подставляются. Единицы не пересчитываются. Число должно быть положительным, не больше 100000 и иметь не более трёх знаков после запятой; для штук разрешены целые количества.

Перед XML исторические обозначения одной основной единицы, например `шт` и `шт.`, объединяются по исходному GUID блюда и GUID основной единицы. Суммирование выполняется в целых тысячных единицы, затем проверяется итоговый предел количества. Зафиксированные количества и события в manifest не меняются. Локальная ошибка такой проверки возвращает определённый `failed` до обращения к iiko и освобождает события; она не считается неизвестным сетевым результатом.

`POST /admin/api/staff/reports/production` принимает только `{requestId, date, eventIds}`: UUID запроса и UUID неизменяемых приходов. Названия, количества, точка, сервер, склады и режим из клиента не принимаются. Точка определяется назначением кассира. В одной транзакции сервер повторно проверяет дату, сброс, версию настройки и неиспользованность событий, рассчитывает количество и сохраняет manifest. Уникальная привязка события к акту предотвращает повтор через другой UUID, перезагрузку или сброс отчёта.

Статусы запроса: `pending`, `sending`, `unknown`, `created`, `failed`. Публичный акт содержит `id`, `date`, `eventIds`, `requestedDocumentNumber`, `postImmediately` и подтверждённый `documentNumber`, если он есть. Ошибки сопровождаются стабильным `errorCode`; текст — пояснение на русском, клиент локализует код.

`POST /admin/api/staff/reports/display-stock/reset` восстановлен для существующего кассового интерфейса: строго `{code:"0000"}` и одна назначенная точка кассира. Код служит подтверждением очистки представления. Сброс не удаляет события, акты или их привязки.

## Подтверждение и восстановление

UUID запроса сохраняется при транспортном сбое. Повтор с тем же UUID и теми же событиями возвращает существующее состояние. Другой набор с тем же UUID отклоняется. Если процесс прервался после сохранения manifest до начала отправки, `pending` можно явно продолжить тем же запросом после новой сессии. GET никогда не отправляет акт.

Непосредственно перед XML-запросом внутри сессии iiko выполняется атомарная проверка `start_cashier_production_http`: запрос ещё находится в `sending`, фактическая отправка ранее не начиналась. Проверка фиксирует время начала; отрицательный результат запрещает XML. Поэтому запоздалый запрос из очереди не отправится после ручного освобождения событий. Повторный XML для `sending`, `unknown`, `created` или `failed` не выполняется. Запрос, оставшийся в `sending` после потери процесса, переводится в `unknown` при чтении после минуты без обновления. Активный запрос текущего процесса не считается потерянным.

Публичная документация не подтверждает безопасный повтор по номеру документа и не предоставляет проверенный поиск актов приготовления, включающий черновики. Поэтому сетевые ошибки, предупреждения и неоднозначные ответы оставляют `unknown` и удерживают события. Успех признаётся только по документированному ответу `documentValidationResult`: `valid=true`, `warning=false`, точное совпадение ожидаемого номера и отсутствие диагностик. Это подтверждение импорта, а не отдельное чтение созданного акта. Номер запроса — `BLK-` и UUID без дефисов; UUID также указан в комментарии XML, но не передаётся как неподдерживаемое поле документа.

Владелец/администратор проверяет завершение обработки и фактический документ в iiko. `GET /admin/api/locations/:id/production-acts` показывает неподтверждённые запросы, зафиксированные сервер/подразделение/склады и названия, GUID, количества и единицы для сверки. Проверка проводится на сервере сохранённого запроса: последующая смена настройки точки не меняет этот контекст. `POST /admin/api/locations/:id/production-acts/:actId/resolve` принимает явное `confirmed=true` и действие:

- `created` с проверенным `documentNumber`: сохраняет привязки событий и статус `created`.
- `not_created`: подтверждает, что обработка завершилась и акт не создан; освобождает события и устанавливает `failed`. Новая отправка требует нового явного UUID. Решение недоступно первые пять минут после фактического начала XML-запроса.

Автор, время и действие проверки сохраняются отдельно от manifest. Повтор того же подтверждения возвращает первый результат; противоречащее подтверждение отклоняется. Поздний ответ первоначального запроса не переписывает ручное конечное решение. Простого отсутствия документа в ещё обрабатываемой очереди недостаточно для `not_created`.

## Документированный iiko-контракт

Используется `POST /resto/api/documents/import/productionDocument`, `Content-Type: application/xml`, корень `<document>`. Поля XML идут в порядке схемы: status, comment, documentNumber, dateIncoming, storeTo, storeFrom, items. Строка содержит amount в основной единице, product GUID, num и amountUnit GUID. Неподдерживаемые ID документа, подразделение и ингредиенты не добавляются.

Источники: [официальная загрузка акта приготовления](https://ru.iiko.help/articles/#!api-documentations/zagruzka-akta-prigotovleniya), [справочники корпорации](https://ru.iiko.help/articles/#!api-documentations/korporatsii), [общие статусы документов](https://ru.iiko.help/articles/#!api-documentations/zagruzka-i-redaktirovanie-prikhodnoy-nakladnoy). Опубликованная XSD не задаёт максимальную длину номера и ограничение типа продукта. Реальный акт при проверке разработки не создавался.
