# Проверка готовности сервера

`GET /readyz` возвращает только `{"status":"ready"}` (200) или
`{"status":"not_ready"}` (503). Любой ответ проверки имеет `Cache-Control: no-store`.
`GET /internal/readiness` требует `METRICS_BEARER_TOKEN` и дополнительно показывает
состояние базы, кассовых доступов, очереди уведомлений, push и фоновых задач.

Каждая проверка ограничена `READINESS_TIMEOUT_MS`: production принимает целое
значение от 500 до 10000 мс, по умолчанию 3000 мс. При превышении срока отменяются
все запросы SDK этой проверки. Ошибка не заменяется предыдущим успешным снимком.
Ошибка чтения кассовых доступов означает `not_ready` даже в compatibility-режиме;
отсутствие настроенного необязательного доступа само по себе не означает сбой базы.

Защищённый снимок и событие `readiness_dependency_failed` содержат безопасный
код `DEPENDENCY_TIMEOUT`, `DATABASE_UNAVAILABLE` или `DEPENDENCY_UNAVAILABLE`.
Сообщения исключений, ключи и детали запросов не публикуются. Общий обработчик
ошибок сохраняет этот узкий диагностический ответ 503; остальные ошибки сервера
по-прежнему скрывают внутренние сведения.

Проверка готовности не подтверждает работу физического кассового оборудования.
Задержка внешней базы может дать 503 при работающем процессе приложения;
`/healthz` и `/livez` не заменяют проверку зависимостей.
