## Подтверждённые проблемы

### P1. Возврат ручной цены к цене iiko не сохраняется

Источник: admin-ui/src/pages/menu/use-menu-page-controller.tsx:377.

При исходной цене iiko 300 и ручной цене 500 ввод 300 и сохранение исключают custom_price из запроса вместо явного удаления override. Сервер сохраняет прежние 500; интерфейс сообщает об успехе и временно показывает 300. После повторной загрузки возвращаются 500. Воспроизведено на опубликованном интерфейсе с подставным API: customPriceSent=OMITTED. Аналогичная логика затрагивает сброс названия; очистка фотографии на строке 383 подставляет прежний URL.

Рекомендация: отдельное действие возврата к данным iiko и явное null для удаления переопределения. Проверить сохранение после повторного чтения сервера.

### P2. Скрытая главная страница продолжает обновлять баннеры

Источник: BulkaAndroid/lib/screens/home_screen.dart:44–48; BulkaAndroid/lib/core/live_refresh.dart:30.

Новый механизм обновления не учитывает видимость вкладки: busy проверяет только загрузку. Старый таймер проверяет TickerMode, новый — нет. Изолированный тест hidden home does not poll and visible home resumes polling повторно завершился ошибкой: после трёх минут скрытого экрана число запросов выросло с 1 до 4. Это лишний трафик и работа в фоне вкладки.

Рекомендация: учитывать видимость экрана, объединить два механизма периодического обновления и обновлять данные при возвращении пользователя.

### P2. Рекомендации пекарни не учитывают её кассовые продажи

Источник: src/services/bought-together.service.js:197.

Для филиала без BOUGHT_TOGETHER_BRANCHES_JSON используется bought-together-online.service и оплаченные онлайн-заказы. В production настроено 0 сопоставлений филиалов. Поэтому покупки на кассе не участвуют в рекомендациях выбранной пекарни; при отсутствии онлайн-истории результат может быть пустым независимо от реальных продаж iiko.

Рекомендация: настроить и проверить сопоставления филиалов с источниками и подразделениями iiko, сопоставить результат с реальными чеками за 30 дней.

### P2. Холодный мобильный запуск остаётся долгим

Production, Chromium, новый контекст без кэша, экран 390×844: первый кадр Flutter через 1,50 с без ограничения сети и через 9,67 с при 4 Мбит/с, задержке 100 мс и замедлении CPU ×4. По одному запуску каждого сценария: это диагностический замер, не статистика реальных клиентов и не измерение нативного AAB.

В медленном сценарии main.dart.js загружался 6,75 с, CanvasKit WASM — 6,61 с. main.dart.js передал около 1,71 MB: прежнее утверждение об отсутствии сжатия нельзя переносить на текущую версию. Ошибок JavaScript не обнаружено. Загрузка изображений не является единственной причиной задержки.

Рекомендация: сокращать критический путь Flutter/renderer, затем измерить серию холодных запусков и готовность к взаимодействию на физических Android/iPhone.

### P2. Полный набор тестов сейчас не проходит

Backend: 1106 тестов — 1096 успешно, 5 ошибок, 5 пропущены. Четыре ошибки bootstrap-font-cache связаны с отсутствием document.head.append в тестовом DOM. Это не подтверждение неисправности production-запуска. Пятая ошибка operational-health зависит от реального порога 25 мс; отдельно все 8 тестов файла проходят.

Flutter: 413 успешно, 14 ошибок. Ошибка скрытого polling подтверждена отдельно как реальный дефект. Остальные сбои преимущественно относятся к каталогу и требуют обновления/проверки fixtures: фоновая проверка выбранной пекарни теперь запрашивает locations, а ряд тестовых API возвращает пустой результат. Не считать все 14 ошибок отдельными пользовательскими багами без воспроизведения.

Рекомендация: исправить реальный polling, привести DOM и API fixtures к контрактам, убрать зависимость health-теста от скорости машины и повторить полный прогон.
