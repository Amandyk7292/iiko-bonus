# Внешняя доставка Яндекса для Bulka

Интеграция поддерживает два несовместимых протокола:

- `cargo_v2` — прежний API Яндекс Доставки;
- `business_v2` — API 2.0 «Яндекс Go для бизнеса» из корпоративного кабинета.

Новые заявки используют выбранный режим, а режим каждой уже созданной заявки хранится
в БД. Поэтому после переключения старые Cargo-заявки продолжают синхронизироваться и
отменяться своим протоколом.

## Подключение Business API

1. В кабинете `business.taxi.yandex.ru` создайте отдельный OAuth-токен. Cargo-токен
   для Business API не подходит.
2. Создайте или выберите служебного корпоративного сотрудника Bulka. У него должен
   быть лимит `taxi`, разрешающий нужную категорию `express` или `courier`.
3. Узнайте `client_id` через `GET /integration/2.0/auth/list` и `user_id` сотрудника.
4. Секреты вводите только в `.env` на VPS — не отправляйте токен в чат, браузерный
   bundle или мобильное приложение.
5. Примените релиз и миграцию, затем задайте:

   ```dotenv
   YANDEX_DELIVERY_ENABLED=true
   YANDEX_DELIVERY_API_MODE=business_v2
   YANDEX_DELIVERY_AUTO_DISPATCH=false
   YANDEX_DELIVERY_SENDER_PHONE=+77000000000
   YANDEX_BUSINESS_API_TOKEN=<секрет из Go для бизнеса>
   YANDEX_BUSINESS_BASE_URL=https://b2b-api.go.yandex.ru
   YANDEX_BUSINESS_CORP_CLIENT_ID=<client_id>
   YANDEX_BUSINESS_USER_ID=<user_id служебного сотрудника>
   YANDEX_BUSINESS_TARIFF_CLASS=express
   YANDEX_BUSINESS_MAX_PRICE_KZT=<жёсткий предел одной поездки>
   YANDEX_BUSINESS_QUOTE_MAX_AGE_SECONDS=120
   YANDEX_BUSINESS_REQUIRED_REQUIREMENTS=<точные ключи из zoneinfo через запятую>
   YANDEX_BUSINESS_RESTAURANT_DELIVERY_CONFIRMED=true
   OPS_ALERT_WEBHOOK_URL=https://ops.example.kz/bulka-alerts
   OPS_ALERT_RECEIVER_REQUIRED=true
   RUN_BACKGROUND_WORKERS=true
   RUN_YANDEX_DELIVERY_WORKER=true
   YANDEX_BUSINESS_ALLOW_PAID_CANCEL=false
   ```

Токен в `YANDEX_BUSINESS_API_TOKEN` указывается только значением токена. Клиент
сам добавляет заголовок `Authorization: Bearer ...`; если в переменную случайно
вставили полное значение `Bearer <token>` или `OAuth <token>`, префикс будет удалён
автоматически. `X-YaTaxi-Selected-Corp-Client-Id` не добавляется к `/auth/list`,
а используется только после получения списка клиентов.

Если `/auth/list` отвечает `401`, это означает, что сам OAuth-токен отклонён до
проверки `client_id`: ID компании и Trace/Request ID не заменяют токен. Получите
новый токен именно для Business API от нужного аккаунта, проверьте его снова и
передайте поддержке только время запроса и полученный от API Request/Trace ID.
Полный токен в тикет или чат не отправляйте.

`YANDEX_DELIVERY_AUTO_DISPATCH` для Business API должен оставаться `false`: после
принятия заказа кухня переводит вызов в «Ожидается подтверждение цены», а owner/admin
сначала получает свежий расчёт и явно подтверждает точную сумму.

## Безопасная проверка перед первым заказом

Проверки выполняются без `orders/create`:

1. `GET /auth/list` подтверждает токен и корпоративный кабинет.
2. `GET /zoneinfo` по координатам филиала подтверждает тариф и возвращает точные
   поддерживаемые `requirements`.
3. `POST /orders/routestats` рассчитывает маршрут и фиксированную цену, но не вызывает
   курьера.
4. Запишите в `YANDEX_BUSINESS_REQUIRED_REQUIREMENTS` только точные ключи,
   объявленные выбранным тарифом в `/zoneinfo`. Имена Cargo API (`auto_courier`,
   `thermobag`) нельзя переносить автоматически. Если согласованная с Яндексом
   обязательная опция отсутствует, сервер останавливается до создания заказа.
5. До canary получите у менеджера Яндекса письменное подтверждение, что выбранные
   тариф и требования разрешены этому кабинету именно для ресторанной доставки в Актау,
   а маршрут поддерживает контакт получателя (`extra_data.contact_phone`) и адресные
   поля, используемые официальным SDK Business API.
   Только после этого установите `YANDEX_BUSINESS_RESTAURANT_DELIVERY_CONFIRMED=true`.
   Без флага backend блокирует платный `/orders/create`. До первого платного вызова
   также настройте и проверьте HTTPS-приёмник тревог, включите оба worker-а и затем
   установите `OPS_ALERT_RECEIVER_REQUIRED=true`.
6. Только после успешного расчёта выполните один ручной canary-заказ с контролируемыми
   телефоном и адресом, работающей точкой выдачи и заранее согласованным лимитом цены.

Если после восьми безопасных повторов статус стал `creating_exhausted`, owner/admin с MFA
обязан открыть корпоративный кабинет и выбрать в диспетчерской одно из двух действий:
ввести найденный ID заказа Яндекса или подтвердить с причиной, что заявка не была создана.
До этого заказ остаётся зарезервированным и второго курьера назначить нельзя.

## Рабочий процесс Business API

1. Клиент оплачивает заказ доставки; оплата сама курьера не вызывает.
2. Сотрудник пробивает заказ в iikoFront и принимает его на кухне.
3. Диспетчер рассчитывает цену. Сервер сначала запрашивает `/zoneinfo`, пропускает
   только действительно поддерживаемые опции и затем вызывает `/orders/routestats`.
4. Вызвать курьера могут только `owner` и `admin`. Интерфейс показывает фиксированную
   цену и просит отдельное подтверждение «Вызвать до N ₸».
5. `/orders/create` получает уже сохранённый UUID в `X-Idempotency-Token`. При timeout,
   HTTP 500 или неоднозначном HTTP 410 сервер не вызывает другого провайдера и повторяет только тот же
   логический заказ с тем же UUID и зашифрованным payload.
6. Статусы запрашиваются через `/orders/progress` и `/orders/info`. Передача еды
   разрешается лишь при статусе ожидания у точки и наличии данных автомобиля.
7. Перед отменой сервер повторно читает `cancel_rules`. `paid`/`minimal` по умолчанию
   запрещены; точная сумма отмены Business API может быть неизвестна.

## Ограничения Business API

- Это employee-centric API: заказ создаётся от служебного сотрудника Bulka, а не от
  покупателя.
- Документация не обещает товарную опись, вес, COD, возврат, proof-of-delivery,
  tracking URL или webhooks. Интеграция передаёт только разрешённые маршрутные и
  контактные поля, а статусы получает polling-ом.
- Business-статус `expired` означает, что состояние заказа неизвестно. Такая заявка
  остаётся активной, блокирует второго курьера и требует ручной проверки/отмены — она
  не считается автоматически завершённой.
- Телефон, адрес, offer и retry-payload не сохраняются открыто в техническом JSON;
  повторяемый create-payload защищён AES-GCM и привязан к job/order.
- Цена Яндекса является расходом Bulka и не меняет уже оплаченную клиентом стоимость.
- `branch_manager` и `operator` могут получить расчёт, но не могут создать платную
  внешнюю заявку.
- Нельзя откатывать приложение на версию без Business-адаптера, пока в журнале есть
  хотя бы одна `business_v2` заявка или необработанная тревога Яндекса. Rollback-скрипт
  проверяет это после остановки пишущего production-процесса и восстанавливает его,
  если откат небезопасен.

## Возврат к Cargo v2

Переключение `YANDEX_DELIVERY_API_MODE=cargo_v2` влияет только на новые заявки. Для
Cargo остаются `YANDEX_DELIVERY_API_TOKEN`, `YANDEX_DELIVERY_BASE_URL`, размеры груза
и остальные параметры из `.env.example`. Не удаляйте legacy Cargo-токен, пока есть
активные `cargo_v2` строки: worker выбирает протокол по самой заявке. Не используйте неопределённый Business-заказ
как повод вызвать второго Cargo- или внутреннего курьера.
